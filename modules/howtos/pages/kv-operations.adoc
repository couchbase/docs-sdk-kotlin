Every KV (Data Service) method in the Kotlin SDK is a Kotlin _suspending function_, so you call it from inside a coroutine.
The Kotlin SDK has no separate asynchronous or reactive API like the Java SDK's `collection.async()` and `collection.reactive()`; suspending functions cover those use cases.
If you are not yet comfortable with suspending functions, see the https://kotlinlang.org/docs/coroutines-basics.html[Kotlin coroutines guide^].

== JSON
 
The Couchbase Server is a key-value store that's agnostic to what's stored, but it's very common to store JSON so most of the examples below will focus on that use-case.
 
In Kotlin, you can pass a `Map` or `List` as document content, and the SDK's JSON serializer encodes it transparently.
When you read a document back, use `contentAs<T>()` on the result — for example `contentAs<Map<String, Any?>>()`.
The SDK also supports custom serializers and transcoders.
See xref:howtos:json.adoc[Working with JSON] for details, including how to use your own classes as document content.
 
Kotlin `Map` and `List` values are immutable.
Where the Java examples mutate a `JsonObject` in place, the Kotlin examples build a new `Map` --
for example with the `+` operator -- and pass that to `replace`.

=== Pessimistic locking
 
Optimistic locking assumes nobody else will change the document while you work with it, and starts again if somebody does.
Pessimistic locking does the opposite: it stops anyone except you from changing the document.
 
`getAndLock` fetches the document and locks it.
While the document is locked, only a caller who knows the CAS value returned by `getAndLock` can modify it.

[source,kotlin]
----
include::devguide:example$kotlin/KvOperations.kt[tag=pessimistic-lock,indent=0]
----
 
The lock is released when you change the document using the correct CAS, when you call `unlock`, or automatically when the lock time expires.
The lock time can be as short as 1 second, or as long as 30 seconds.
 
Pessimistic locking is expensive.
It's usually better to use optimistic locking.

== Durability
 
Writes in Couchbase are written to a single node, and from there the Couchbase Server will take care of sending that mutation to any configured replicas.
 
The optional `durability` parameter, which all mutating operations accept, allows the application to wait until this replication (or persistence) is successful before proceeding.
 
It can be used like this:
 
[source,kotlin]
----
include::devguide:example$kotlin/KvOperations.kt[tag=durability,indent=0]
----
 
If no argument is provided (the same as `Durability.none()`) the application will report success back as soon as the primary node has acknowledged the mutation in its memory.
However, we recognize that there are times when the application needs that extra certainty that especially vital mutations have been successfully replicated, and the other durability options provide the means to achieve this.


If you need stronger durability guarantees,
you can take advantage of the xref:concept-docs:durability-replication-failure-considerations.adoc#durable-writes[Durable Write] feature, 
in which Couchbase Server (self-managed or Capella) will only return success to the SDK after the requested replication level has been achieved. 
The three replication levels are:

* `Durability.majority()` -- The server will ensure that the change is available in memory on the majority of configured replicas.
* `Durability.majorityAndPersistToActive()` -- Majority level, plus persisted to disk on the active node.
* `Durability.persistToMajority()` -- Majority level, plus persisted to disk on the majority of configured replicas.
 
The options are in increasing levels of safety.
Note that nothing comes for free -- for a given node, waiting for writes to storage is considerably slower than waiting for it to be available in-memory.
These tradeoffs, as well as which settings may be tuned, are discussed in the xref:concept-docs:durability-replication-failure-considerations.adoc#durable-writes[durability page].





This durability is enforced by the cluster.
A client verified durability API was necessary with older, no longer supported version of Couchbase Server.
Here the SDK does a simple poll of the replicas and only return once the requested durability level is achieved.

This API is still avaialable, but there are few cases where you would want to use this less performant option.
Should you need to consider it, here is an example:

To stress, durability is a useful feature but should not be the default for most applications, as there is a performance consideration,

== Atomic Counters
 
The value of a document can be increased or decreased atomically using `collection.binary.increment()` and `collection.binary.decrement()`.

NOTE: Increment & Decrement are considered part of the "binary" API and as such may still be subject to change


[source,kotlin]
----
include::devguide:example$kotlin/KvOperations.kt[tag=counter,indent=0]
----
 
The `delta` is an unsigned number (`ULong`), so write literals with a `u` suffix, like `1u`.
If the counter document does not exist, `initialValue` decides what happens: if it is `null`, the call throws `DocumentNotFoundException`; otherwise the document is created with that value, and that value is returned (the `delta` is ignored).


TIP: Setting the document expiry time only works when a document is created, and it is not possible to update the expiry time of an existing counter document with the Increment method -- to do this during an increment, use the `touch` method.
 
See the https://docs.couchbase.com/sdk-api/couchbase-kotlin-client/kotlin-client/com.couchbase.client.kotlin/-binary-collection/index.html[API Reference^] for full details.

== KV Range Scan
 
A range scan gives you documents from a collection, even if you don't know the document IDs.
This feature requires Couchbase Server 7.6 or newer.


TIP: KV range scan is suitable for use cases that require relatively low concurrency and tolerate relatively high latency.
If your application does many scans at once, or requires low latency results, we recommend using {sqlpp} (with a primary index on the collection) instead of KV range scan.

If you use this document naming scheme, you can use a prefix range scan to get all documents associated with a user.
