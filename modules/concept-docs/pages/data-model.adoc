= Data Model
:description: Couchbase's use of JSON as a storage format allows powerful search and query over documents. Map, list, set, and queue structures can be built on documents with the sub-document API.


[abstract]
{description}


Data structures in Couchbase are similar in concept to the data structures in the Kotlin standard library:

* **Map** is like a Kotlin `Map<String, Any?>`, and is a key-value structure, where a value is accessed by using a key string.
* **List** is like a Kotlin `List<Any?>`, and is a sequential data structure.
Values can be placed at the beginning or end of a list, and can be accessed using numeric indexes.
* **Queue** is a wrapper over a _list_ which offers FIFO (first-in-first-out) semantics, allowing it to be used as a lightweight job queue.
* **Set** is a wrapper over a _list_ which ensures each value in the list is unique.

These data structures are stored as JSON documents in Couchbase, and can therefore be accessed using https://www.couchbase.com/products/n1ql[{sqlpp} (formerly N1QL)], Full Text Search, and normal key-value operations.
A map is stored as a JSON object, and a list as a JSON array.


== Data structures in the Kotlin SDK

The Java SDK has a dedicated data structures API: `Collection` methods such as `map()`, `list()`, `set()` and `queue()`, which return implementations of the Java Collections Framework interfaces backed by documents in Couchbase Server.

The Kotlin SDK does not have an equivalent API.
Instead, you build the same structures with the xref:howtos:subdocument-operations.adoc[Sub-Document API], which is what the Java implementations use under the hood.
The examples on this page show how.

Using sub-document operations to treat a document as a container data structure may help your application in two ways:

* **Simplicity**: you can deal with documents as if they were container data structures.
Adding an item to a map is expressed as `upsert("some_key", "value")` in a `mutateIn` call, rather than retrieving the entire document, modifying it locally, and then saving it back to the server.
* **Efficiency**: sub-document operations do not transfer the entire document across the network.
Only the relevant data is exchanged between client and server, allowing for less network overhead and lower latency.

Every call is a Kotlin suspending function, so call these examples from a coroutine.

A queue is a list where you add items at one end and remove them from the other.
In this example `arrayPrepend` adds to the front of the list, so the oldest item is always the last element.

Adding an item is a single sub-document operation.
Removing an item takes two steps: read the last element, then remove it.
Another client could change the queue between those two steps, so the example passes the document's CAS value to the removal, and starts again if the CAS no longer matches.

== Choosing between these patterns and full-document operations

Sub-document operations are a good fit when you only touch a small part of a large document.
If you usually read or write the whole document, the ordinary xref:howtos:kv-operations.adoc[full-document operations] are simpler.

The Java SDK's `CouchbaseMap` has to make at least two sub-document requests for each `put` or `remove`, because the Java `Map` interface requires those methods to return the previous value.
Working with sub-document operations directly, as above, avoids that cost: each mutation in the examples is a single request, except for removing from a queue, where the extra read is the point.

For more detail, see xref:howtos:subdocument-operations.adoc[Sub-Document Operations] and xref:howtos:kv-operations.adoc[Data Operations].
